# 第 2 轮收敛（静态审阅，未运行任何测试）

## 1. 撤回与修订

- **撤回“12 轮 / 24k / 前 1500 字摘要”方案。** 它仍是有损截断，只是从静默变成了标注，没有根治续问失忆。接受方案 A：超限时显式拒绝，并保留原文。
- **撤回“正文前几段 + 展开全文”。** 接受方案 C：直接显示全文。
- **修订“文献移出后整轮只发提问”。** 这会制造新的失忆。应把两件事分开处理：
  - **历史数据**：保留回答全文，因为它是用户可见的对话。
  - **本轮原文授权**：历史只作上下文，不能当证据。
  - **最小防护**：发送前用 `mapCitationNumbers` 把历史里的 `[n]` 改写为 `〔前轮引用〕`。对已移出的文档追加标注“已移出本研究，不可引用”。本轮引用仍只认本轮 `read_page` 并通过 quote 校验的内容。
- **`:295` 疑点由“待复现”升级为“事实”。** 依据补充的正则：代码块和链接之外的 `[n]` 都会被转换。只要 n 超出 `sourceIds`，或为 0、负数，就会抛错，例如 `[2023]`、参考列表“[1] 作者”、数组下标。模型是否真会输出这类内容，仍待验证。

## 2. 必须修的风险（最多 5 条）

**R1（事实）：引用编号会静默错配。**
- `remap` 只检查编号对应的索引是否存在。
- 如果模型照抄了历史中的 `[3]`，而本轮恰好读过 3 页，它会被静默映射到另一篇论文，不会报错。
- 修法：上文的历史编号中和是必修项。每个 `[n]` 是否都有 quote 校验，待验证。

**R2（事实）：方案 D 的候选列表会触发整轮失败。**
- 如果模型在正文中用 `[1]…[10]` 列出 `search_literature` 的候选，就会触发抛错，整轮失败。
- 修法：候选只能通过 typed 事件和卡片呈现。instructions 禁止为未读文献编号。
- 另需保证：引用校验失败时，已生成的正文要作为失败轮可见保留，不能丢弃。当前是否会丢，待验证。

**R3（待验证）：方案 B 的恢复存在竞态。**
- 恢复必须按 `ownerConversationId + requestId` 定位。只有同时满足以下条件才恢复：
  - 该请求仍是该会话的最新请求；
  - composer 的 `trim()` 为空；
  - drawing 为空。
  - 不能依赖 `current()`。
- 其他要堵住的情况：
  - 双击发送：在同一 tick 加 in-flight 锁，并用客户端 requestId 去重。
  - 切换会话后才收到失败事件。
  - 点击停止后立即打字。
  - 恢复原文后用户又点了重试，造成重复发送。
- 需确认：清空附件时会不会 revoke 已被请求冻结的 objectURL。

**R4（事实 / 待验证）：方案 A 的容量与一致性。**
- 120000 字符不等于 token 数。run 内 `read_page` 的返回还会继续占用预算。
- 因此预检通过后，供应商仍可能拒绝。这种情况必须走 R3 的保原文路径。
- 服务端目前限制是 8000（事实），必须与客户端使用同一个计算函数，同步放宽。

**R5（待验证）：方案 D 的边界。**
- **配额**：每轮 3 次 / 10 条必须由服务端按 runId 强制，不能只靠 instructions。
- **停止与重试**：停止时，部分候选以 stopped 状态落盘；重试生成新的 runId，不复用旧配额，也不重复写入候选。
- **研究归属**：“加入本研究”的 researchId 由服务端从 conversation 推导并校验，不能取前端当前选中的研究。
- **不可信内容**：摘要可能含提示注入，必须标为不可信。
- **查询词**：“只发关键词”无法强制，只能限制在 500 字以内，并把查询词展示在执行记录里。

## 3. 最小验收矩阵
